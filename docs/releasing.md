# Releasing

Saymore releases are built by `.github/workflows/release.yaml`. The workflow is
started manually from the GitHub Actions page. It creates the release tag on the
already-reviewed `main` head after that commit has passed CI, then builds from
that tag without modifying its source. Ordinary pushes and small changes are
covered by CI without automatically publishing a new stable version.

This document currently covers direct distribution through GitHub Releases. The
planned Mac App Store submission and release workflow will be documented
separately when its packaging and review requirements are implemented.

GitHub supplies the latest Release tag and whether the requested tag already
exists in `main`; the tested `cargo run -p xtask -- release-plan` command owns
version validation. A new tag is created only after the `main` head's CI run has
passed. A packaging retry reuses an existing tag only when it resolves to the
current `main` head and its workspace still declares the requested version; it
does not silently change that tag to publish newer code.

## Versioning

The workspace version in the root `Cargo.toml` is the only application version
source. Before starting a new release, use the pinned manifest editor to update
all inherited workspace and internal path-dependency versions together:

```bash
cargo install cargo-edit --version 0.13.13 --locked
cargo set-version --workspace 0.3.0
```

Replace `0.3.0` with the intended release version. Commit the resulting
`Cargo.toml` and `Cargo.lock` changes using the repository's required review and
push gates. A new release must increase beyond the latest `vMAJOR.MINOR.PATCH`
GitHub Release; an unchanged workspace no longer implicitly produces another
patch release. The manual workflow's required `version` input must match this
committed workspace version. Repeating the same run reuses that exact
current-head tag when repairing its Release.

After successful CI for the version commit, start **Release** manually. The
workflow creates an annotated tag on that same commit before packaging starts.
Both platform jobs check out the tag and revalidate its workspace version; they
never run `cargo set-version`. The publish job creates the GitHub Release from
that tag. The workflow never creates a release commit, pushes to `main`, or
creates a second post-release CI run solely to validate its own version edit.
The macOS `CFBundleVersion` is a monotonically increasing UTC build timestamp
generated by `cargo-packager`.

For a new tag, the release plan requires a successful `CI` push run for the
exact source commit before tagging and packaging. Reruns at the same head reuse
the already-reviewed tag but still rebuild and verify both packages. CI runs
formatting, lints, doc tests, and the size budget once on macOS, tests every
workspace target on macOS and Windows, and builds the production desktop binary
in release mode on pushes to `main`. Dependency policy runs separately on
Ubuntu. Pull requests stop at the quality and test gates, so release packaging
is not repeated for every review.

Packaging installs Rust 1.99.0, matching `rust-toolchain.toml` and CI. Both
macOS targets must be installed for that exact toolchain; installing them only
for the moving `stable` channel leaves the pinned compiler without the Intel
standard library when the versions differ. Update the release toolchain pins
together with the repository and CI pins when upgrading Rust.

## Artifacts

- macOS builds both Apple Silicon and Intel targets, combines them into one
  universal binary, and publishes a branded drag-to-Applications DMG plus
  SHA-256 checksums to GitHub Releases. The repository-owned DMG background,
  window size, and icon positions are declared in the desktop package metadata.
  The DMG opens directly to its Finder window without an install-time license
  agreement. With complete Apple credentials, packaging signs and notarizes the
  application, signs the final DMG, submits that DMG to Apple, staples the
  accepted ticket, and requires Gatekeeper to accept it before upload. The
  workflow then mounts the generated image without accepting an EULA and
  verifies its background, Finder layout metadata, application bundle, and
  Applications link. Signed releases also require the mounted application to
  pass strict code-signing validation for every architecture, contain the Audio
  Input entitlement required for microphone capture, and pass Gatekeeper
  execution assessment. Regenerate the committed background after design changes
  with `swift apps/desktop/packaging/macos/generate-dmg-background.swift`.
  Without complete Apple credentials, the DMG filename ends in `-unsigned.dmg`.
- Windows builds an NSIS installer named `Saymore-Setup.exe` and publishes it,
  together with its SHA-256 checksum, to the same GitHub Release.

Linux is not built or published until its platform adapters are implemented and
the Linux target is explicitly restored to CI and the release workflow.

## Required Repository Configuration

Set the workflow permission to allow GitHub Actions to write repository
contents. The workflow needs this permission only to create the annotated tag
and upload the GitHub Release. It does not commit or push `main`; no branch-rule
exception for release commits is required.

Each platform must be signed; packaging fails closed when a credential set is
incomplete instead of silently publishing an unsigned package. The
`allow_unsigned` dispatch input is the only escape hatch: it produces
`*-unsigned` artifacts and creates the GitHub Release as a draft that is never
marked latest. Use it for a deliberate unsigned build, never as a routine path.

macOS secrets for click-to-open distribution (join the Apple Developer Program):

- `APPLE_CERTIFICATE`: base64-encoded Developer ID Application `.p12` file.
- `APPLE_CERTIFICATE_PASSWORD`: password used when exporting the `.p12` file.
- `APPLE_ID`: Apple account used for notarization.
- `APPLE_PASSWORD`: app-specific password for that account.
- `APPLE_TEAM_ID`: Apple Developer team identifier.

All five must be present. A partial configuration now fails the packaging job
and names the missing secrets, because a half-configured identity cannot sign
and notarize reliably.

Windows secrets for Authenticode signing:

- `WINDOWS_CERTIFICATE`: base64-encoded Authenticode code-signing `.pfx` file.
- `WINDOWS_CERTIFICATE_PASSWORD`: password used when exporting the `.pfx` file.

Both must be present. The packaging job imports the certificate into a temporary
file, signs `Saymore-Setup.exe` with SHA-256 digest and RFC 3161 timestamping,
verifies the result with `signtool verify /pa`, and removes the certificate file
before the job ends.

## macOS User Permissions

Saymore requires microphone permission to record speech. It also requires
Accessibility permission to monitor the configured global dictation shortcut,
identify the focused input control, deliver transcribed text to another
application, and observe a bounded correction to that delivered text. macOS owns
these privacy decisions; the application must not bypass or silently grant them.

The macOS bundle declares `NSMicrophoneUsageDescription` and its code signature
contains `com.apple.security.device.audio-input`. Both are required before
AVFoundation can register Saymore with TCC and present the native microphone
authorization prompt.

The initial onboarding explains and requests these permissions. Its
Accessibility action calls the native macOS trust request so a first-time user
receives the system authorization prompt and can continue into System Settings.
After onboarding, application startup and login launch do not proactively
present the Accessibility reminder. A missing permission is surfaced when the
user opens the permission settings or attempts a shortcut that requires it.

For a correctly signed release, a user grants each permission once for the
installed application identity. Repeated password or Touch ID requests after an
application restart indicate that macOS no longer recognizes the same valid
code-signing identity. Treat that as an application-identity or system-trust
defect rather than removing the permission UI. Check the release package, the
installed copy, and the host macOS version. Verify the installed bundle with:

```bash
codesign --verify --all-architectures --deep --strict --verbose=4 \
  /Applications/Saymore.app
spctl --assess --type execute --verbose=4 /Applications/Saymore.app
```

Development builds must use the persistent `Saymore Preview.app` workflow
documented in `development.md`. Launching `target/debug/saymore-desktop`
directly gives rebuilt binaries changing ad-hoc identities, so macOS cannot
reliably retain their Accessibility authorization.

## Recovery

Once a tag exists, rerunning the workflow at the same `main` head reuses that
tag, rebuilds the same version, and creates or repairs the Release assets. It
preserves an existing Release title and notes; it does not move the tag to
another commit. Start a new review and version commit if the release source
needs to change.

If a tag exists without a complete Release and `main` has advanced, repair it
from that tag's commit through a reviewed maintenance process rather than
silently assigning its version to newer code. The regular manual dispatch does
not backfill an older tag. An unfinished or incorrectly tagged source can be
left without a public Release while a new, higher version is prepared; document
that discarded tag in this file's recovery notes.

The new pre-tag CI guard applies only to subsequent releases. A pre-existing tag
created by the old workflow can still be repaired even though its own release
commit did not have a separate CI run.

### October 26, 2026 manual packaging recovery

[The manual release run](https://github.com/PraxisGrove/Saymore/actions/runs/40285450233)
produced the Windows installer but failed to compile the Intel macOS target. The
moving `stable` action installed targets for Rust 1.99.1 while Cargo used the
repository's pinned 1.99.0 compiler. Both packaging jobs now install the pinned
version explicitly. Local standard-library probes succeeded for both macOS
architectures with Rust 1.99.0.

The recovery push also encountered new RustSec advisories. The lockfile updates
Rustls to 0.23.46, rustls-webpki to 0.103.16, Tokio to 1.53.3, and webpki-roots
to 1.0.10. Dependency auditing passes with those patches. The release still
requires the complete push gate and successful CI for the repaired source commit
before another manual packaging run.
